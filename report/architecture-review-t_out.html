Problem

Every caller knows fd, count[], the zero-init ritual, and two meanings of silent.

Solution

One module owns sink, tally, silent mode, and future bench metadata behind named constructors and queries.

  • locality: silent semantics in one module
  • leverage: one interface, many call sites
  • tests stop reading ctx.count[]
  • bench gets a natural home

Problem

One operation has four representations, so renames drift and the compiler catches none of it.

Solution

A table keyed by t_op carries name and checker token; op_emit derives text.

  • locality: add an operation once
  • leverage: emitter, checker, tests share one table
  • interface shrinks: drop the name parameter
  • tests assert operation and name together

Problem

Tests redirect stdout to see bytes, while counts cannot show order or pairing.

Solution

Make the operation stream observable as data, with fd and in-memory log adapters behind one session.

  • tests assert sequence and pairing
  • no global stdout redirection
  • bench stream and tally diverge cleanly
  • sort tests observe operations

Problem

Every sorter and helper forwards a, b, and out; sort functions never inspect the output context.

Solution

A run context owns both stacks and the operation session; sort strategies cross one interface.

  • locality: run state in one module
  • sort interface shrinks to one parameter
  • checker stops manufacturing a sink
  • broad blast radius; sequence after Candidate 1

Top recommendation

Start with Candidate 02, then Candidate 01.

One operation definition is the smaller, sharper change: it removes the four-vocabulary drift before the operation session module absorbs op_emit. Then t_out gets one home for silent mode, counters, and benchmark metadata.
